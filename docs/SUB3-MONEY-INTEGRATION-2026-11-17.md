# Dominion Sub3 · Money integration (2026-11-17)

The `dominion-sub3` branch now includes the Money research UI and its entire source-backed business opportunity pipeline, adapted to the independent Rust SDK. Only this branch changed.

## Execution architecture

- **UI:** `web/src/pages/Money.tsx`, navigation in `WorkspaceShell.tsx` and lazy route in `App.tsx`. Investigate from archived SQLite observations, optionally ask an existing agent to reason once, or enable a budgeted recurring research campaign.
- **Zero-token acquisition:** `money_sources` ingests public RSS/news; `money_catalog` captures GitHub/Hugging Face technology activity; `money_folding` converts source revisions into events and indexed asymmetries. The domain uses the existing SSRF-guarded `http_fetch` adapter.
- **Durable store:** `src/db/money.rs` implements the Money methods as a child extension of **the same** `Store`. `money_schema.sql` adds FTS5, indexed fact terms, entity/date, source, active-status and market-pair indexes. All candidate/source/report commits use the shared SQLite transactions, not a competing database.
- **Ranking improvements:** publication age uses the source's published date, not crawl time. Syndicated identical headlines on different hosts are not accepted as independent market evidence. Explicit buyer requests and directly fetched pages receive bounded priority, not claims of actual revenue.
- **Verified quote-to-revision binding:** buyer demand claims now require an exact normalized match in a stored fetched article body (or legacy saved excerpt); an RSS headline or description cannot alone validate buyer intent. Evidence carries the immutable `sourceRevisionId` from the same atomic signal/revision ingestion transaction, so reviewers can identify the precise captured text version. Buyer-cited pages also store up to 16,000 characters of body and keep the 2,000-character retrieval excerpt. Purchase/payment status remains unconfirmed unless separately evidenced.
- **2026-11-18 decision support:** New `db/money_review.rs` and `api/money_review.rs` provide owner-controlled defer/reject/restore with atomic append-only `money_review` history. The paginated `/api/money/archive` searches low-rank and previously hidden hypotheses; deferred/rejected records are excluded only from the next active shortlist, not removed from storage. Money GUI opens the human review history and stored source text. All read paths use bounded SQLite retrieval without another model.
- **Source revisions:** `money_ingest_signals` captures immutable SHA-256 content revisions on first observation and on page-text enrichment. `money_sources` preserves up to 16,000 characters of extracted article text in `articleBody`, while `articleExcerpt` stays capped at 2,000 characters for indexing and prompt efficiency. Headline twins are recorded in `money_source_alias` with original URL, publisher and publication date but are not treated as independently confirmed market demand. The source API reports archived material as observation, never proof of a transaction. Older signal records remain compatible even when they have no prior revision.
- **Hypothesis generation:** `money_mechanism`, `money_asymmetry`, `money_intelligence`, `money_retrieval`, `money_rank`, and the added evidence-prioritized, cross-publisher diversity selection rank causal opportunities. Publication date is preferred over crawl date, two independent sources over a headline, and explicit buyer requests over unsupported estimates. All amounts with no evidence remain unknown.
- **Model inference:** `money_discover` is dispatched by sub3's existing `engine::jobs` worker into **`native_agent::run`** and the independent Rust SDK. Input `prompt` is a short, non-mutating research task; detailed market evidence is passed via `ownerInstructions` to avoid misclassifying quoted source text as file-edit authorization. Tools and MCP are disabled, actual model calls capped at 3, and native SDK has a 4,000–120,000 token ceiling. Text-only/compat 27B models may return plain JSON, normalized to the SDK's terminal `answer` envelope; native-tool-capable providers already return plain final answers.
- **Money reliability:** stale or expired autopilot markers are disabled before any additional source collection, so abandoned campaigns cannot keep the collector awake. The source collector treats successful but unchanged RSS reads as healthy, and combines new signals with bounded historical observations in the same acquisition cycle. Money inference rejects cancelled jobs before auxiliary fetches, while the candidate/report/fact commit atomically verifies a still-running shared job under SQLite's transaction lock. User edits and all older records remain untouched.
- **Architecture comparison:** Qwen Code's shared headless core/UI/SDK adapters (https://github.com/QwenLM/qwen-code/blob/main/docs/developers/architecture.md) and OpenHands SDK's persisted events/conversation state (https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/state.py) were compared on 2026-11-18. Sub3's Money archive remains a detachable domain module on the existing SQLite and host job interface; no second execution loop is added.
- **Design reference:** 2026 public OpenHands SDK execution state and LangGraph persisted interruption documentation illustrate that execution state must own lifecycle and durable checkpoint state; DOMINION keeps that state inside the existing Rust job and SQLite transaction rather than adding a second Money agent loop.
- **Idle efficiency:** the host retains its 30-second approval housekeeping interval but calls the optional Money scheduling hook only once every 60 seconds (50% fewer idle plug-in marker lookups). Explicit user enable still schedules immediately. No second worker, database, or always-on model loop.
- **Plug-in boundary:** `src/engine/plugins.rs` registers Money job kinds into the existing host queue. Money stays dormant at startup unless an explicitly enabled saved campaign needs recovery; per-user collection and analysis execute when requested, with the same SQLite database and no duplicate engine. The optional host heartbeat checks enabled campaigns, not independent domain workers.
- **Shared Rust checkpoint ownership:** `JobContext::checkpoint` delegates to `Store::checkpoint_running_job`; it atomically checks `status=running`, the claimed worker attempt and cancellation flag. Earlier attempts cannot publish progress or terminal output after a newer retry, cancellation or completion. This applies to Money implementation and all host jobs without a second plugin loop.
- **Owner-approved implementation handoff:** `POST /api/money/candidates/:id/implement` requires `approved=true`, a selected stored agent and a bounded token budget; it atomically stores the candidate's approval receipt together with a deterministic `prompt` job in the SAME SQLite transaction (`src/db/money_implementation.rs`). Concurrent/repeated approval returns the original job and cannot overwrite an orphaned job ID. No separate runtime or DB. `GET /api/money/candidates/:id/implementation` provides a durable status lookup; `GET /api/money/find` embeds compact implementation job state for refresh, cancellation and session navigation. Candidate edits use atomic field updates so a stale editor cannot erase approval linkage.
- **Money UI execution:** completed Rust jobs store domain payloads under `job.result.result`; the UI now reads that envelope and the persisted execution record for model calls and estimated tokens. Money offers native `/api/jobs/:id/cancel` for ongoing inference, explicit candidate rejection, and a user-confirmed, tool-allowlisted prototype implementation job using the existing Rust SDK. No external purchase, customer contact or deployment is approved by that action.
- **Persistence and agency:** all saved candidates have source provenance and speculative status; rejected hypotheses and reported business outcomes feed existing deduplication and follow-up. First revenue is a user-reported or independently witnessed event, not a model guess. Unattended research uses the shared maintenance heartbeat, single campaign claims, and restart-safe run IDs; external commercial actions remain user-controlled.

## Public interfaces

- `GET|POST /api/money/find` and `GET /api/money/stats` are directly connected to the Money UI.
- The full campaign, candidate, experiments, validation-kit, and autopilot endpoints remain available.
- `sdk/typescript` and `sdk/rust` expose Money calls without launching another execution framework.

## Verification and limits

`Sub3 Money domain acceptance` GitHub Actions verifies the Rust domain algorithms, SQLite/API unit tests, native JSON envelope, TypeScript page build, and lean-product checks. Ordinary Money CI runs only scoped Rust `cargo test` commands in the development profile, using one macOS runner; no frontend build, Node checks, `cargo check`, release build, or platform-wide matrix runs on push. The Windows/macOS full gate, GUI/SDK builds, packaging and platform verification are reserved for the manually triggered release stage.

This implementation does **not** claim real revenue, 27B long-running performance, external customer confirmation or model success rates without measured jobs. It never runs unapproved purchases, outreach or deployment.
